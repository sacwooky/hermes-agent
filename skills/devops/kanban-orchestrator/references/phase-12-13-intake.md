## Phase 12: Decomposition Requires Packet

**Rule:** Before an orchestrator decomposes a goal into child kanban cards, an approval packet MUST exist on-file for that decomposition.

### What qualifies as a packet

An approval packet is a written document (markdown, PRD, decision memo) that includes:

1. **Scope statement** — what work is being decomposed and why
2. **Acceptance criteria** — what "done" looks like for the whole body of work
3. **Risk assessment** — what could go wrong and how it's mitigated
4. **Approval signature** — the operator (Keith) has signed or explicitly approved

The packet can live in:
- The Conductor vault (`docs/prds/` or `docs/plans/`)
- A project-local `docs/` directory committed to the repo
- The kanban card body itself (for small scopes), IF the card body contains all four elements above

### Existing grandfathered packets

These predate Phase 12 and are accepted without additional evidence:

1. `APPROVAL-conductor-gate-hardening-2026-06-06.md` — the gate-hardening follow-up epic
2. `conductor-vault-v0-rc1-release-note-2026-06-03.md` — the v0 RC1 release
3. Any `docs/prds/APPROVAL-*.md` file committed before 2026-06-06

### Enforcement

The orchestrator's `kanban_create` fan-out MUST check for packet existence BEFORE creating child cards. If no packet is found:

1. **STOP** — do not create children
2. **Block the orchestrator card** with reason: `packet-required: decomposition of "<goal>" has no approval packet on-file`
3. **Optionally suggest** what the packet should cover

This is a hard gate, not a warning. An orchestrator that decomposes without a packet is a coordination defect (see Phase 13).

## Phase 13: Unannounced Work Is Coordination Defect

**Rule:** Kanban cards that appear on the board representing new work — especially decomposition/fan-out cards — without a corresponding approval packet or prior operator acknowledgment constitute a coordination defect.

### What "unannounced work" means

Unannounced work is any card that:
- Creates new deliverables, features, or changes not covered by an existing approved packet
- Introduces new dependencies, costs, risks, or operational changes
- Was generated by an agent without operator knowledge or approval

This does NOT apply to:
- Repair cards for existing approved work (bugfixes, review fixes, resolver cards)
- Documentation updates that clarify existing work
- Maintenance tasks (dependency bumps, lint fixes, drift repair)

### Detection

The orchestrator skill's decomposition step should flag unannounced work by checking:
1. Does a packet exist for this scope? (Phase 12 check)
2. Was this work discussed in a prior session? (session_search)
3. Does an existing board epic or story already cover it?

If all three are negative, the work is unannounced.

### Response to coordination defect

When unannounced work is detected:

1. **Do NOT create child cards** for the unannounced work
2. **Comment on the originating card** explaining that the work lacks an approval packet
3. **Block with a clear reason** naming what's missing and what packet would cover it
4. **Notify the operator** via the card block notification

The operator can then:
- Approve the work verbally → orchestrator creates the packet retrospectively
- Provide a packet → orchestrator resumes decomposition
- Reject the work → card is cancelled/archived

## Relationship to the Slice 4/5 incident

The incident at `runs/2026-06-05-003` demonstrated what happens when decomposition bypasses approval:
- Work was created and dispatched without operator visibility
- Workers executed on a scope the operator hadn't signed
- Coordination overhead grew because multiple agents were operating on unclear authority

Phase 12 and Phase 13 are the direct corrective actions from that incident.
